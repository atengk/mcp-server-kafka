# 领域文档规范与消费规则 (Domain Docs)

本文档规范了各项工程智能体（Engineering Skills）在理解、探索和维护本项目代码库时，如何消费和遵循领域的上下文与设计文档。

## 探索代码库前的前置阅读要求

在对业务代码开展深度探索或方案设计前，必须按顺序检查并阅读以下核心文档：

1. **`CONTEXT.md`**：位于项目根目录，定义了全系统的领域边界、核心业务实体概念（Ubiquitous Language）及核心术语表；
2. **`docs/adr/`**：系统架构决策记录（Architecture Decision Records）。阅读与即将开展的工作区域相关的历史决策；
3. **静默兼容策略**：若上述任何文件暂未建立，**请保持静默并直接继续执行**。严禁主动将缺失文件报错或强行在需求前置步骤中打断提示。相关领域模型与决策记录将由 `/domain-modeling` 技能在概念真正确定或冲突时按需创建。

## 目录结构规范

本项目采用**单上下文架构 (Single-context)**：

```text
.
├── CONTEXT.md               # 核心领域术语表与系统业务上下文 (按需建立)
├── docs/
│   ├── adr/                 # 全局架构决策记录 (ADRs)
│   │   ├── 0001-xxxx.md
│   │   └── 0002-xxxx.md
│   └── agents/              # 智能体工程配置文档
│       ├── domain.md
│       ├── issue-tracker.md
│       └── triage-labels.md
└── src/                     # 业务源码目录
```

## 严格遵循统一术语表 (Use the glossary's vocabulary)

当在交付物中提及任何领域概念时（包括 Issue 标题、重构建议、技术方案、函数/类命名以及测试用例名称）：
- 必须严格采用 [`CONTEXT.md`](../../CONTEXT.md) 中已定义的统一术语；
- 严禁擅自引入统一术语表已经明确规避或弃用的同义词；
- 若当前遇到无法映射的新概念，这表明：要么你在使用项目未采用的冗余术语（请重新思考审视），要么当前领域模型存在空白（请记录并在后续通过 `/domain-modeling` 补充定型）。

## 显式标注 ADR 决策冲突 (Flag ADR conflicts)

如果新的设计或技术方案与既有的历史架构决策记录（ADR）存在冲突，**严禁静默覆盖**，必须在方案中显式暴露并陈述重评原因：

> ⚠️ *该方案与历史决策 [ADR-0001](./docs/adr/0001-xxx.md) 存在冲突，建议重新评审该决策，原因如下：...*
