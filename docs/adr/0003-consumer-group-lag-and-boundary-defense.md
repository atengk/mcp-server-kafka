# 0003: 消费组积压 (Lag) 诊断算法与边界防御策略

针对大语言模型与 AI 智能体在评估 Kafka 消费端健康度、计算各分区消息积压 (Lag) 以及排查消费者倾斜卡死等运维场景，我们决定采用基于集群现存物理拓扑的 Lag 精确计算算法，并建立针对已删除主题和未提交位移新分区的边界防御机制。

## 决策背景

1. **已删除主题的悬空位移导致网络挂死**：Kafka 的 `__consumer_offsets` 内部主题会长期保留历史消费组的已提交位移。当某个主题已被业务方物理删除，位移元数据可能依然残留。若直接将已删除主题的 `TopicPartition` 提交至 `consumer.end_offsets(...)` 请求高水位，会导致客户端长时间阻塞超时甚至挂起。
2. **分区扩容与新分区的无位移状态**：在主题物理分区横向扩容或新消费者刚加入尚未提交位移时，其 `committed_offset` 为空或为 -1。若简单按缺失处理或抛出异常，会导致监控漏报或诊断流程崩溃；实际上，未提交位移的分区所有数据均属潜在待消费积压，其真实积压量应精确等同于当前日志末端位移 (LEO)。
3. **倾斜与断连分析依赖全量物理视图**：单纯查询已提交位移无法发现“未被任何成员分配、且从未提交位移的新扩容分区”，必须将涉足主题的全部物理分区纳入拓扑视图，方能精准识别“消费者挂死/分区饥饿 (Starvation)”。

## 决策内容

1. **已删除主题前置过滤与状态标定**：
   - 在向底层 Consumer 发起 `end_offsets` 查询前，必须先获取当前集群现存的所有主题列表 (`list_topics`)；
   - 过滤分离出已从集群中物理删除的主题分区，严格禁止对其实例化高水位探测；
   - 在返回结果中将该类分区标定为 `topic_deleted=True`，并将 `log_end_offset` 与 `lag` 均置为 `None`，不计入总积压量 (`total_lag`)。
2. **涉足主题物理分区自动补齐**：
   - 收集已提交位移与活跃成员已分配分区的并集，提取所涉足的所有现存主题；
   - 调用主题详情接口获取各涉足主题的所有物理分区，补齐未被分配或尚未提交位移的新分区；
   - 对尚未提交位移的新分区 (`committed_offset is None`)，将其 `lag` 计算为 `log_end_offset`，真实反映全量未消费积压。
3. **空消费组自适应处理**：
   - 对无任何活跃成员或从未产生提交位移的空消费组 (`state="Empty"`)，返回空列表并安全将 `total_lag` 设为 0，杜绝空指针或异常中断。
4. **诊断 Prompt 模版多维联动**：
   - 配合专有提示词 `diagnose_topic_lag`，引导大模型按分区倾斜 (Partition Skew)、成员断连 (Consumer Dead)、心跳超时导致重平衡等维度开展根因归因。
